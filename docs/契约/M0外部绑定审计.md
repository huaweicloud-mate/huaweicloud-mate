# M0 外部绑定审计

状态：Implementation unblocked; release inputs remain

审计日期：2026-07-14

本文件只核验 Proposed v0.3-lite 已要求的外部绑定，不重新评估或扩展既有架构。没有达到证据门槛的项目保持未绑定，不用示例值、浮动 URL 或推测性 issuer 填充正式契约。

## 2. 四宿主审批 issuer

### 2.1 Codex

当前运行环境可观察到宿主对部分工具操作进行用户审批，但本轮未能从可访问的 OpenAI 官方资料中确认以下接口：

- 宿主审批事件的稳定回调；
- 可验证 issuer identity 或 verifier key；
- 将 `previewId`、challenge 和参数摘要绑定进 receipt 的机制；
- 阻止 Agent 直接调用签发器的宿主保证。

OpenAI Codex 手册抓取因代理响应缺少完整性头失败，OpenAI Docs MCP 的本地添加也被系统拒绝执行。因此 Codex 暂不绑定 issuer，不能把普通工具审批弹窗直接等同于 `approvalReceipt`。

### 2.2 Claude Code

Claude Code 官方 CLI 提供 `--permission-prompt-tool`，可在非交互模式把权限请求交给指定 MCP tool。这是最接近宿主审批桥接的候选机制，但公开 CLI 说明尚不足以证明该 tool 对 Agent 不可见、返回值能够绑定 Router challenge，或交互模式具有等价机制。

结论：保留为候选，不冻结 issuer ID。需要最小集成验证后才能采用。

来源：[Claude Code CLI reference](https://docs.anthropic.com/en/docs/claude-code/cli-usage)

### 2.3 OpenCode

OpenCode 可以对指定 MCP tool 配置 `ask`，并提供 `once / always / reject` 用户选择。该机制可以作为执行前门禁，但公开文档没有定义把批准事件转换为 Router 可验证签名 receipt 的接口；`--auto` 还会自动批准原本为 `ask` 的请求，因此不能直接作为强制安全边界。

结论：原生 `ask` 只能作为候选触发点，不冻结 issuer ID。

来源：[OpenCode permissions](https://opencode.ai/docs/permissions/)、[OpenCode tools](https://opencode.ai/docs/tools/)

### 2.4 华为云码道

码道 CLI 支持 `allow / ask / deny`，`ask` 提供 `Allow once / Allow always / Reject`；码道也支持 stdio、SSE 和 Streamable HTTP MCP。但当前权限文档列出的管控对象未给出 MCP tool 审批事件的签名回调或 receipt 导出接口。

结论：确认存在用户审批 UI，但不能据此冻结 issuer ID。

来源：[码道 CLI 权限](https://support.huaweicloud.com/usermanual-cli/codeartsagent_cli_0006.html)、[码道 MCP](https://support.huaweicloud.com/usermanual-codeartssnap/codeartsdoer_ug_0010.html)

### 2.5 已确认决定

采用 ADR-0008 允许的第二种方式：四宿主统一使用 npm 内置、按需启动且不作为普通 Tool 暴露的受信 companion，由明确用户操作触发签名。

- issuer ID：`huaweicloud-mate.local-approval`；
- verifier key ID：`local-approval-ed25519-v1`；
- 算法：Ed25519；
- 密钥：每次审批进程在内存生成独立密钥对，通过 Router 创建的私有继承管道绑定临时公钥和 `approvalSessionId`，结束后销毁；
- 禁止：自动批准、`--yes`、环境变量批准、Agent/Prompt/Skill 可调用签发路径。

当前 TypeScript 核心已经实现并覆盖：一次性内存密钥、strict review/ready/result message、session ID 绑定、完整 runtime artifact manifest/逐文件 SHA-256、最小子进程环境、私有 Node IPC、无 inspector/SIGUSR1 调试入口、随机且一次读取的 loopback 审批页、Host/Origin/CSRF/CSP/字段/时限限制、终端/HTML 转义、字段/签名篡改、错误 session 公钥、五分钟时效、最小 Router preview/execute 原子消费、进程重启使 pending preview 失效、凭证代次变化、并发重放、执行器锁定和结果未知不回退。`doctor --approval-probe` 使用相同 launcher 完成无凭证、无云副作用的 challenge/receipt 探测。

stdio MCP 已通过真实子进程测试确认只暴露 `search / describe / execute`，并接入静态开发态 catalog、普通 read、危险两阶段调用、结构化错误及 JSON Pointer 脱敏。ADR-0010 已冻结第二阶段：Agent 只提交相同输入和 `previewId`，Router 在调用内部启动 companion、验签回执、复核身份并原子 dispatch；公开 schema 明确拒绝 `approvalReceipt`。协议层不需要第四个 Tool、未定义 metadata 或自动批准。

ADR-0035 已把 M0 最初 3 个状态机向量纳入构建后 doctor：approval replay、`OUTCOME_UNKNOWN` 后执行器锁定、credential generation 变化均由真实无云 Router/session harness 执行；ADR-0046 又加入产品 MCP 执行前不可用时选择安全 KooCLI Adapter 的向量。当前 4 个状态机向量 deferred 为 0；Provider handshake digest mismatch 也会执行语义比较，不再只依赖 schema 合法性。

它尚未形成正式安全边界，仍需：

- 完成正式产品 capability/Provider 与 KooCLI 执行器接线；本地 OBS capability、账号校验、provider dispatch 和进程重启后 pending preview 失效验证已完成；
- 版本目录、完整 install manifest、稳定 launcher、失败不切换和安装/卸载边界的用户目录递归权限门禁已实现；仍需发布 provenance，并降低摘要校验到模块加载间的同账号替换窗口；
- 在四宿主验证 Agent sandbox 无法读取私有 IPC、枚举审批 URL/CSRF、自动提交表单、调试、注入或转储 companion；无法满足时不得宣称强制审批；
- 在 Codex、Claude Code、OpenCode 和华为云码道实际运行 `doctor --approval-probe`，记录交互与隔离证据。

后续工作是集成与安全加固，而不是继续选择审批模式。

## 3. 首发能力与后续产品 MCP

公开官方资料可确认：

- DWS 提供产品级 MCP Server，但能力围绕 DWS 元数据、监控和 SQL；
- AgentArts 提供 MCP 网关调用接口，但它是平台网关能力，不等同于满足本项目 Provider descriptor 的 ECS/OBS 产品 MCP；
- 当前资料没有给出与 MCP data plane 同源的 `/credential-sessions`、route token、capability digest 和 tool schema digest 组合。

这是基于官方资料的范围判断，不代表其他内部产品 MCP 不存在。ADR-0048 已确认真实产品 MCP 不进入首版。reference provider 继续明确标记为无凭证、无网络测试 fixture；内置本地 OBS provider 使用官方签名协议实现 `ListBuckets`、有界文本对象读取、创建私有桶和删除空桶，以最长 900 秒内存 session、generation、route token、provider instance 和 Owner ID 绑定打通 auth 与 Router。创建桶固定进入 `write + privileged + cost` 点击审批，删除空桶固定进入 `write + destructive + privileged` 点击审批；请求发出后的网络中断返回 `OUTCOME_UNKNOWN` 且不重试。它不冒充 Streamable HTTP 产品 MCP；真实 MCP 到位后仍经保留的 endpoint/session client、health 和 digest 接口静态接入。

后续产品 MCP 集成前仍需要产品团队直接提供至少一个真实 Provider 的正式输入：

- 产品、owner 和责任人；
- data plane、credential session、health 的同源 HTTPS endpoint；
- Provider contract 和版本范围；
- capability/tool schema 与 SHA-256 digest；
- session、route token、日志脱敏和 AK/SK 内存生命周期责任边界；
- `auth set` 固定只读账号身份校验能力。

来源：[DWS MCP Server](https://support.huaweicloud.com/devg-911-dws/dws_04_1464.html)、[AgentArts MCP 网关调用](https://support.huaweicloud.com/api-agentarts/InvokeMcpGateway.html)

## 4. KooCLI

用户已确认首版正式 KooCLI 使用华为云官方快速安装页面列出的安装包。ADR-0048 将私有版本固定为 `7.2.12`，系统预装兼容范围保持 `>=7.2.2 <8.0.0`。Windows amd64、Linux amd64/arm64、macOS amd64/arm64 五个同名官方区域镜像制品已实际下载并计算 SHA-256，均与官方 `.sha256` 文件一致；Windows amd64 解包后的原生命令报告 `7.2.12`。

官方对象使用 `/cli/latest/`，因此供应链语义改为“精确官方路径 + 插件内置摘要”，而不是运行时跟随 latest：

- 只接受固定官方 host、五个精确文件名、无查询参数/fragment/重定向的 HTTPS URL；
- release manifest 内置五个 `7.2.12` SHA-256，安装器对下载字节重新计算摘要；
- 上游替换对象后，已发布插件必须摘要失配并停止安装，直到新插件版本重新取证；
- ZIP/`tar.gz` 安全解包、版本化私有目录、原子提交、可执行文件 hash 和 `hcloud version` 复核保持不变。

制品来源与摘要已完成绑定。官方资料没有提供非 argv、非持久 profile 的 AK/SK 注入方式；Windows 隔离 home 实测也失败。用户随后明确接受无配置 argv 风险，ADR-0050 已实现受限 invoker；没有静态 capability mapping 或 credentials 时仍 fail closed。

2026-07-15 在当前 Windows amd64 开发机对系统安装 KooCLI 做了无凭证只读验证：原生命令报告 `7.2.12`，构建后的 `doctor --koocli` 将其识别为 `PASS (compatible, 7.2.12, system)`。ADR-0051 随后静态绑定 `ECS ListServersDetails`，要求 region/project、1～50 的 limit、可选 UUID marker、`sensitive-read` 点击审批，并在 KooCLI 内固定裁剪为 ID/名称/状态。无云测试已覆盖审批前零 dispatch 和审批后授权 argv；认证/只读云调用、最小权限与元数据下载仍待真实账号验收。

来源：[KooCLI 最新动态](https://support.huaweicloud.com/wtsnew-hcli/index.html)、[KooCLI 下载与校验文件](https://support.huaweicloud.com/qs-hcli/hcli_02_003.html)、[华为云官方 skills 安装指南](https://github.com/huaweicloud/huaweicloud-skills/blob/master/skills/bss/billing/huawei-cloud-billing-scout/references/cli-installation-guide.md)

## 5. 端到端场景

保留现有 5 个场景，不再增加场景类型：

1. OBS 普通读取与执行前补位；
2. ECS 创建的复合风险审批；
3. VPC 公网暴露与执行器锁定；
4. ECS 删除后的 `OUTCOME_UNKNOWN`；
5. OBS 对象敏感读取。

场景行为已经足以冻结；“真实端到端”仍需产品和测试责任人补齐 capability ID、endpoint/digest、测试 region/project、最小权限账号、资源规格、清理责任人和宿主分配。

## 6. 下一步输入清单

按发布阻塞优先级收集：

1. 首个 ECS KooCLI capability 的元数据可用性与最小权限账号验收；mapping、五平台制品、摘要和 argv invoker 已完成；
2. 统一受信 companion 的四宿主隔离验证、交互责任人和私钥保护测试；
3. 首版本地 OBS/KooCLI 场景的最小权限测试账号、region/project、资源规格和清理责任人；
4. 公共 npm scope 与发布身份。

真实产品 MCP owner 与 endpoint/contract 包移至后续版本接入清单。上述首版输入补齐后，只需填充既有 schema、模板和场景，不需要恢复 Proposed v0.2 的复杂设计。
